# 보이스닥터 원고 생성 (월·화 각 3편)

## 발행 주기

| 항목 | 값 |
|---|---|
| 발행 요일 | **월요일, 화요일** (주 2회) |
| 1회 편수 | **3편** (골라서 발행) |
| 주간 생성량 | 6편 |
| 원고 도착 | 발행 당일 아침 06:57 (한국시간) |
| Routine cron | `57 21 * * 0,1` (UTC 기준 — 일·월 21:57 = 한국 월·화 06:57) |

수요일~일요일에는 원고를 만들지 않습니다.

## 0. 실행 전 반드시 읽을 것

```
brand/tone-and-manner.md   ← 말투·구조·제목 공식 (실측) + H섹션(발행본 반영, 최우선)
revisions/                 ← 사장님이 고쳐 발행한 원고
brand/guardrails.md        ← 유사문서·법적 리스크 규칙
brand/profile.md           ← CTA·브랜드 정보
corpus/*.md                ← 원본 글 (톤의 정답지)
keywords/queue.tsv         ← 오늘 쓸 키워드 후보
keywords/used.tsv          ← 이미 쓴 키워드 (제외 대상)
drafts/                    ← 최근 생성분 (유사도 비교 대상)
```

가드레일과 톤앤매너가 충돌하면 **가드레일이 이깁니다.**

## 0-2. 최신 스타일 확인 (매 실행)

원고를 쓰기 전에 **최신 기준**을 먼저 확인한다. 우선순위 순서다.

### 1순위 — 사장님이 고쳐 발행한 원고

`brand/tone-and-manner.md` 의 **H섹션**을 읽는다.
여기 적힌 규칙은 A~F의 실측값보다 우선한다.
`revisions/` 에 새 발행본이 들어와 있는데 H섹션에 반영되지 않았다면,
`scripts/compare_revision.py` 를 돌려 차이를 확인하고 결과를 보고에 포함한다.

### 2순위 — 네이버 상위노출 문서 확인

오늘 쓸 키워드로 실제 상위노출 중인 글을 확인해 최신 흐름을 반영한다.

**단, 이 환경은 네이버 도메인이 조직 네트워크 정책으로 차단되어 있다.**
`blog.naver.com` `search.naver.com` `openapi.naver.com` 모두 CONNECT 403 이다.

- 접근이 **가능해졌다면**: 키워드별 상위 3~5개 글의 제목 형태, 분량,
  소제목 구성, 도입부 훅을 확인하고 그 흐름을 반영한다.
- 접근이 **여전히 막혀 있다면**: 확인을 시도했으나 차단되었다는 사실을
  보고에 한 줄로 남긴다. 추측으로 "요즘 트렌드는 이렇다"고 쓰지 않는다.
  corpus와 H섹션을 기준으로 쓴다.

접근 여부는 매번 실제로 확인한다. 정책은 바뀔 수 있다.

```bash
curl -sS --max-time 10 -o /dev/null -w "%{http_code}\n" https://search.naver.com/
```

## 1. 키워드 선정

1. `keywords/queue.tsv` 에서 `status=ready` 인 행을 읽는다
2. `keywords/used.tsv` 에 있는 키워드는 제외
3. **최근 60일 내 사용 키워드와 의미가 겹치면 제외** (예: "발성연습 방법" / "발성 연습하는 법")
4. **3개**를 고를 때 타깃 독자가 서로 다르게 조합한다

   | 슬롯 | 타깃 | 성격 |
   |---|---|---|
   | A | 일반인 | 검색량이 큰 대표 키워드 |
   | B | 지망생·현직 직업군 | 전환이 좋은 키워드 |
   | C | 특정 증상·고민 | 경쟁이 낮은 롱테일 |

   같은 날 세 편이 같은 독자를 겨냥하면 자기 글끼리 경쟁합니다.
   월요일과 화요일 사이에도 타깃이 겹치지 않게 합니다.

   사장님이 3편 중 골라서 발행하시므로, **버리는 편이 생겨도 괜찮게**
   세 편의 성격을 뚜렷이 다르게 만듭니다. 비슷한 세 편은 고를 이유가 없습니다.

5. queue가 8개 미만이면 `keywords/seed.md` 를 읽어 확장하고 queue에 채운다
6. queue가 4개 미만이면 **원고 생성을 중단하고 사장님께 알린다** (임의 키워드 생성 금지)

## 2. 원고 작성

### 분량 (실측 기준 — 반드시 지킬 것)

- 공백 제외 **1,900 ~ 2,400자** (corpus 실측 최소 1,905 / 최대 2,530)
- 줄바꿈 블록 **55~70개** (발행본 실측 65 / 57), 평균 문장 25~30자
- 초과하면 줄인다. 길게 쓰는 게 좋은 게 아니다.

### 골격

`tone-and-manner.md` C섹션의 12단계를 따르되,
**유사문서 방지를 위해 3~4단계는 순서를 바꾸거나 생략한다.**

변주 예시:
```
표준 : 훅 → 반전 → 재정의 → 비유 → 브랜드 → 영상 → 요약 → 차별화 → 해부학 → 1:1 → CTA
변주1: 증상나열 → 재정의 → 브랜드 → 영상 → 요약 → 해부학 → 비유 → 차별화 → 1:1 → CTA
변주2: 독자속마음 → 반전 → 비유 → 해부학 → 브랜드 → 영상 → 요약 → 1:1 → 차별화 → CTA
```

### 줄바꿈 — 가장 중요

이 블로그의 정체성입니다. 문단을 붙여 쓰면 안 됩니다.

- 1~2문장마다 줄바꿈
- 의미 단락 사이 빈 줄 **3~6개**
- 긴 문장은 어절 단위로 끊어 다음 줄로

### 매번 겹치는 정형 구간 — 여기서 유사도 검사가 걸린다

실제 생성 이력에서 유사도 검사에 걸린 문장은 거의 전부 아래 네 구간이었습니다.
사실이나 메시지가 같아서가 아니라 **문장을 같은 방식으로 썼기 때문**입니다.
매 글 다른 표현으로 씁니다.

| 구간 | 겹친 예 | 대응 |
|---|---|---|
| 영상 안내 | "훈련 전후를 담은 영상을 아래에…" | 문장 구조를 매번 바꾼다 |
| 원인 열거 | "어떤 분은 갈비뼈가 거의 움직이지 않고…" | 열거 개수·순서·주어를 바꾼다 |
| 쉬면 나아지는 이유 | "쉬면 나아지는 이유도 여기서 설명됩니다" | 설명 각도를 바꾼다 |
| 마무리 서사 | "마지막에 오시는 경우였습니다" | 매번 다른 장면으로 쓴다 |

영상 안내 변주 예
- 바로 아래에서 훈련 전후 소리를 비교해 보실 수 있습니다
- 회원분들의 훈련 전과 후 소리를 아래에서 들어보실 수 있습니다
- 훈련 전과 후를 담은 영상을 아래에 올려두었습니다
- 아래 영상에는 회원분의 전후 소리가 함께 담겨 있습니다

원인 열거 변주 예
- "같은 증상을 가진 열 분이 오시면 막혀 있는 지점은 열 군데가 다릅니다"
- "'목소리가 작다'는 말은 증상이지 원인이 아닙니다"
- "같은 통증을 말씀하셔도 시작점이 제각각입니다"

### 해부학 설명 — 가장 겹치기 쉬운 구간

횡격막·갈비뼈·복횡근·골반기저근 설명은 거의 모든 글에 나옵니다.
사실은 같아도 **매번 다른 방식으로 서술**해야 합니다. 진입점을 바꾸세요.

| 진입점 | 서술 예 |
|---|---|
| 들숨에서 시작 | 숨이 들어올 때 무엇이 움직이는지부터 |
| 압력에서 시작 | 소리가 무엇 위에 얹혀 나가는지부터 |
| 실패 지점에서 시작 | 이 근육이 일을 안 하면 어디가 대신 일하는지부터 |
| 자세에서 시작 | 정렬이 무너지면 왜 호흡이 흔들리는지부터 |
| 비교로 시작 | 조용히 말할 때와 길게 말할 때의 차이부터 |

같은 진입점을 이틀 연속 쓰지 않습니다.

### 제목 6개 뽑기

`tone-and-manner.md` E섹션의 유형표를 따릅니다. **유형이 겹치면 안 됩니다.**

| 순위 | 유형 | 비고 |
|---|---|---|
| 1 | **부정형** | `~는 건 ~가 아닙니다` — 1편 발행에서 채택 |
| 2 | **단정형** | `~는 이유는 ~ 문제` — 2편 발행에서 채택 |
| 3 | 원인형 | `~좋아지지 않는 이유` — corpus 4편, 상위노출 중 |
| 4 | 방법형 | |
| 5 | 증상형 | |
| 6 | 질문형 | |
| 예비 | 대상형 · 비교형 | 위 6개로 못 채울 때만 |

**제목에서 답을 말한다.** 두 발행본 모두 현상을 묻지 않고 결론을 박았다.
현상 제시·질문형에 치우치지 않는다.

체크리스트
- [ ] 메인 키워드가 **맨 앞**에 있는가 (6개 전부)
- [ ] 키워드가 제목 안에서 **1회만** 나오는가
- [ ] 18~30자인가 (모바일에서 잘리지 않게)
- [ ] 특수문자·이모지·물음표 남용이 없는가 (질문형의 `~일까요`는 허용)
- [ ] 6개가 서로 다른 검색 의도를 겨냥하는가
- [ ] 본문이 그 제목의 의도에 실제로 답하는가 (제목만 바꾼 낚시 금지)

frontmatter에는 `유형 | 제목` 형식으로 적습니다.

```yaml
titles:
  - 원인형 | 강사 목소리 아무리 관리해도 오후만 되면 무너지는 이유
  - 방법형 | 강사 목소리 관리 목캔디보다 먼저 해야 할 것
```

### 반드시 들어갈 것

> 아래는 `tone-and-manner.md` H섹션의 확정 규칙이다. **예외 없이 적용한다.**

- 브랜드 인사 `17년 차 발성 전문 트레이닝 센터 보이스 닥터입니다` — **`안녕하세요`를 붙이지 않는다** (H1)
- CTA 마지막 줄은 `먼저 문의하신 뒤 일정 조율 부탁드립니다.` 앞머리는 `아래로` / `아래 안내에 따라` (H2)
- 병원을 서사 주체로 언급하지 않는다. 질환 관련 진료 안내는 유지 (H3)
- CTA 직전에 마무리 한 마디를 둔다. 원리 요약이거나 권유 (H4)
- 시간·기간 한정(`오전/오후`, `몇 년째`)을 붙이지 않는다 (H5)
- **나열은 0~2개.** 필요 없으면 뺀다 (H6)
- 비유는 문답으로 전개하고 결론은 짧게 (H7)
- 설명 전환에 물음표 반문을 쓴다 (H8)
- **`~죠` 어미를 쓰지 않는다** (H9)
- **블록을 잘게 쪼개지 않는다.** 평균 문장 25~30자 (H10)
- `여러분` 4회 이상, `보이스 닥터` 2회 이상 (H11)
- 브랜드 인사 직전에 전환 예고 문장 `지금부터 ~ 이야기해 보겠습니다` (H12)
- `저희 센터는 ~ 학원이 아닙니다` 선언을 넣는다 (H13)
- 비포&애프터 영상 자리 + 면책 괄호
- `[접기/펴기]` 요약 3~5문장 (메인 키워드 포함)
- 브랜드 도그마 최소 3개 (`방법이 아니라 상태` / `소리를 잘 낼 수 있는 상태` / `오직 1:1` / `각자 원인이 다르다`)
- CTA: 회원제, 당일 방문 불가, 사전 연락
  **실제 전화번호·카카오 채널명은 넣지 않는다** (방침). corpus와 같은 문형으로 끝낸다

## 3. 자체 검수 (통과 못하면 재작성)

각 원고에 대해 순서대로 검사한다.

| # | 항목 | 기준 | 불통과 시 |
|---|---|---|---|
| 1 | 글자수 | 공백 제외 1,800~2,300 | 재작성 |
| 2 | **유사문서** | corpus 4편 + drafts 최근 60일 + 당일 다른 2편과 **연속 15자 이상 일치 없음** (도그마 문구 제외) | 해당 문장 재작성 |
| 3 | 금지 표현 | `치료` `완치` `처방` `환자` `부작용 없는` `100%` `무조건` `최고` `1위` | 자동 치환 후 재검사 |
| 4 | 배타성 표현 | `유일` `최초` 는 사장님 확정으로 허용. 그 외 `최고` `1위` 는 금지 | 치환 |
| 5 | 질환명 횟수 | 3회 이상 → ⚠️ 플래그 | 사람 검수 표시 |
| 6 | 도그마 | 최소 3개 포함 | 보강 |
| 7 | 줄바꿈 | 블록 55~70개 | 재구성 |
| 8 | 키워드 | 제목 맨 앞 **1회만** + 첫 문단 1회 + 본문 3~5회 | 조정 |
| 9 | 제목 후보 | **6개, 유형이 모두 다를 것**, 각 20~30자 | 재생성 |

유사문서 검사는 아래로 수행한다.

```bash
python3 scripts/check_similarity.py drafts/<날짜>/<파일>.md
```

## 5. 발행

1. `drafts/` 커밋
2. `keywords/used.tsv` 에 3행 추가 (발행 여부는 사장님이 고른 뒤 갱신), `queue.tsv` 상태 갱신
3. `delivery/artifact-url.txt` 의 URL을 읽어 **같은 주소로** 웹페이지 갱신 발행
   - 파일이 비어 있으면 새로 발행하고 URL을 저장한다
   - 발행 전 반드시 `Artifact action:"read"` 로 현재 버전을 읽고 그 위에 갱신한다
4. 웹페이지 구성
   - 오늘 원고 3편: 제목 후보 6개 / 본문 / 태그 / 이미지 지시
   - 각 블록마다 **복사 버튼**
   - ⚠️ 플래그가 있으면 상단에 눈에 띄게 표시
   - 페이지에는 지난 날짜가 모두 담긴다. 상단 날짜 칩으로 골라 볼 수 있다
   - 빌더가 `drafts/` 전체를 읽으므로 과거 원고를 지우지 않는다
5. 커밋 & 푸시. **푸시가 실제로 반영됐는지 확인한다.**

```bash
git push -u origin claude/voicedoctor-blog-automation-ngm8m2
git rev-parse HEAD
git ls-remote origin claude/voicedoctor-blog-automation-ngm8m2   # 두 값이 같아야 한다
```

두 해시가 다르면 **푸시가 실패한 것이다.** 이때는 재시도하고,
그래도 안 되면 **보고 맨 위에 실패 사실을 크게 남긴다.**
아티팩트만 갱신되고 저장소에 원고가 없으면 다음 실행이 그 원고를
모르기 때문에 키워드 중복과 유사문서 위험이 생긴다.

> 2026-09-08 실행에서 실제로 이 일이 있었다. 원고 3편이 아티팩트
> 안에만 존재했고 저장소에는 없었다. 라이브 페이지에서 복구했다.
